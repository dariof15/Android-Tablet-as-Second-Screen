# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Not a conventional software project: it is a working **system integration** that turns an
Android tablet into a second screen over USB-C, on GNOME/Wayland where the usual X11 recipe
(`xrandr --newmode` + `x11vnc`) cannot work. See `README.md` for the user-facing view.

There is no build, no test suite, and no linter. "Correct" means the services come up and a
virtual monitor appears on the tablet. Verification is done by querying live system state
(D-Bus, `xrandr`, `adb`, journals), so **prefer measuring over reasoning** — several
conclusions here were reached by measurement and contradicted the obvious guess.

Developed against: Ubuntu 24.04, GNOME Shell 46 on Wayland, Intel i7-1355U / Iris Xe
(**no NVIDIA**), Xiaomi Pad 8 Pro at 3200x2136 (3:2), Android 16.

## Architecture

```
mjpeg-screen.py    virtual monitor -> JPEG -> HTTP MJPEG on 127.0.0.1:$HTTP_PORT
auto-layout.py     pins that monitor beside the built-in panel
usb-tunnel.sh      adb reverse on every replug + tablet keep-awake
settings.py        shared .env loader used by both Python scripts
install.sh         generates + enables the three systemd user units
bench.sh           encoder CPU as % of ONE core
```

Units are `tablet-screen`, `tablet-screen-layout`, `tablet-screen-tunnel` (systemd **user**
services). They are **generated by `install.sh`**, not committed, because they need the
absolute path of the checkout — never hand-write them with a hardcoded path.

### The virtual monitor mechanism

Everything rests on non-obvious behaviour of Mutter's ScreenCast API (version 4):

- `Session.RecordVirtual({"is-platform": True, ...})` creates a monitor that **actually
  extends the desktop**. Without `is-platform: True` you get an invisible capture surface
  and no monitor — verified empirically both ways.
- **The consumer sets the resolution.** Mutter sizes the virtual monitor from the
  capsfilter placed immediately after `pipewiresrc`. There is no size argument in the D-Bus
  call, and `Meta-0` reports exactly one mode, dictated by whoever consumes it.
- Stopping the session removes the monitor, which is what makes the on-demand lifecycle
  possible.

### Configuration

`.env` (gitignored; `.env.example` is the committed template). Precedence is
**CLI flag > environment variable > `.env` > default**, implemented in `settings.py`.

The scripts load `.env` themselves rather than using systemd's `EnvironmentFile=`, so a
manual terminal run behaves identically to the service. `usb-tunnel.sh` has its own small
parser for the same file. If you add a setting, add it to `.env.example` **and** the README
table.

## Hard-won constraints

All verified on this machine; re-deriving them costs a lot of time.

**JPEG needs full-range colorimetry.** `colorimetry=1:4:7:1` before `jpegenc` is mandatory.
GStreamer otherwise emits limited-range (16-235) YUV while JPEG is defined full-range, so
the decoder mis-stretches it: mean channel error 17.4, whites clipped at 248, visibly
washed out. With it, mean error 0.45. **Do not "simplify" this away.**

**`vaapijpegenc` cannot encode Y444 on this Intel driver** (`Internal data stream error`),
only 4:2:2/4:2:0 — which cost max channel errors of 255 on sharp edges. Hence software
`jpegenc` with Y444 is the default: ~163 fps at 1536x1024, ~12 ms CPU/frame, 5x the
headroom needed for 30 fps. `ENCODER=hw` is ~3.7 ms/frame but mean error 7.3.

**Mutter gives every virtual monitor a fresh serial** (`0x000003`, `0x000004`, …), so
`~/.config/monitors.xml` never matches and GNOME reverts to a default arrangement on every
connect. That is the entire reason `auto-layout.py` exists. It applies a *temporary* config
on purpose — persistent applies append a dead stanza per connection.

**`svc power stayon usb` does not work.** Over USB-C PD the tablet reports
`AC powered: true / USB powered: false`, so the USB-only bitmask never matches. Use
`svc power stayon true` and confirm `mStayOn=true` in `dumpsys power`.

**`adb reverse` mappings die on unplug** — they live in the adb device connection. That is
what `usb-tunnel.sh` loops on, via `adb wait-for-usb-device` / `adb wait-for-usb-disconnect`.

### Why the RDP path was removed (do not reintroduce it)

GNOME Remote Desktop in `extend` mode works and carries touch input, so it looks
attractive. It was built, measured, and deleted:

- **No H.264 exists on this system.** grd 46 has only `HW_ACCEL_API_NVENC` (NVIDIA), and
  Ubuntu's FreeRDP is built `WITH_GFX_H264=OFF`, `WITH_OPENH264=OFF`, `WITH_VAAPI=OFF`. A
  journal line saying `H264 (AVC444): true` only reports what the *client* claimed.
- So RDP always uses RemoteFX progressive (coarse tile, then refinement), which produces
  artifacts flickering in and out under the cursor. Unfixable: lowering resolution reduces
  churn but not the codec, and disabling client input changes nothing (input costs almost
  no CPU).
- **grd hard-requires the Graphics Pipeline.** Unchecking `RDP Gfx` in a client yields
  `Client did not advertise support for the Graphics Pipeline, closing connection`, which
  surfaces on the tablet as a misleading *credentials prompt*. The binary contains a
  "neither support RFX nor GFX / legacy path" warning string, but that path does not work.

## Gotchas when working here

- **`bench.sh` is confounded by on-screen activity.** It cannot control what the desktop is
  doing, so samples taken during different activity are not comparable. A 4x apparent
  regression was once pure measurement noise. Keep the tablet idle or repeat the identical
  action, and treat single samples as indicative only.
- **Never use `pkill -f <pattern>`** where the pattern also appears in your own command
  line — Bash tool invocations match themselves and the shell dies mid-command (this
  silently ate a heredoc). Iterate `pgrep -x python3` and check `/proc/$p/cmdline`.
- Frames are only produced on damage, so a static desktop yields single-digit fps. Low fps
  in `/stats` is expected, not a fault.
- Screenshots pulled with `adb exec-out screencap` contain the user's desktop — delete them
  when done, and note `*.png`/`*.jpg` are gitignored for that reason.
- This is destined for a public repo: keep machine-specific paths, serials, and hostnames
  out of committed files.
- **Cold boot works, but not for the reason the units suggest.** Measured on a real reboot:
  all three units reached `active` 29 s after boot with `NRestarts=0`, and plugging the
  tablet in 14 minutes later brought up tunnel, monitor and layout with no intervention.
  `RestartSec=5` was never exercised, so it is *not* what covers the Mutter race — the
  scripts are structurally immune instead. `mjpeg-screen.py` touches Mutter only when a
  viewer appears, which is necessarily after the session exists; `auto-layout.py` does hit
  the race and logs `could not read monitor state: ... without an owner` one second in,
  then keeps watching and applies the layout correctly later. **Preserve that tolerance**:
  making either script exit on an absent Mutter bus name would turn a harmless log line
  into a restart loop. `usb-tunnel.sh` needs no Mutter at all — if only it fails, the
  problem is adb.

## Threading model in `mjpeg-screen.py`

HTTP handlers run on their own threads; D-Bus and GStreamer belong to the GLib loop thread.
Rather than marshal calls across threads, handlers only move a viewer counter, and a 1 Hz
`ScreenManager.reconcile()` tick on the GLib loop makes the world match it — creating the
virtual monitor when viewers appear, destroying it `IDLE_GRACE` seconds after the last one
leaves. Keep that split if you extend it.

`LatestFrame` deliberately holds **only the newest frame**: queueing would convert a slow
client into unbounded latency, which is the entire point of this path. Its `wait_newer`
timeout re-sends the current frame as a keep-alive.

## Not done

Display-only by design. `org.gnome.Mutter.RemoteDesktop` (Version 1) is available and is
the route to injecting taps/keys if input is ever wanted — the same API GNOME's own RDP
server uses.
